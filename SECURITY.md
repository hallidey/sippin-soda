# Security

This project is pre-release and is intended for controlled development traffic. The proxy binds to IPv4 loopback only after explicit Start. It installs no CA and never changes system proxy settings. By default CONNECT forwards an opaque TCP stream, typically TLS, with certificate validation between client and upstream. After separate CA generation, client trust verification, profile authentication and an explicit per-run opt-in, only Development CONNECT destinations may use TLS termination. Production, Unknown and non-ready destinations remain opaque. Direct HTTP Upgrade remains unsupported.

Metadata captures redact complete query strings and retain only allowlisted header values. URL paths remain visible and can contain secrets; do not treat this as complete sensitive-data redaction. Optional body recording is disabled by default. When enabled it stores unredacted, unencrypted decoded response bytes in local temporary files; header redaction does not protect response body contents. JSON request bodies up to 1 MiB are redacted recursively by a built-in sensitive-key policy and optional validated JSON Pointer paths before a separate inspection copy is written to disk. The original request is forwarded unchanged and never written by request inspection. Non-JSON, invalid and oversized request bodies are not recorded. CONNECT payloads are never recorded. See [HTTP proxy limits](docs/HTTP_PROXY.md).

Temporary body files use tempfile's private file creation and independent, securely reopened handles. IPC accepts capture IDs and bounded byte ranges, never paths. Clear, eviction and normal app exit remove owned body files; Stop retains captures for inspection. A crash or forced process termination can leave named temporary files behind, and deletion is not secure erasure. Do not enable raw recording for traffic whose contents must not reach disk. Full sensitive-data redaction and encrypted session storage remain future work.

Body export is available only for completed captures. The Rust host opens the native save dialog and performs the copy directly, so large bodies do not pass through the webview. The safety preview distinguishes redacted request copies from unredacted responses, and exporting a response requires an explicit acknowledgement. Exported files are user-owned, unencrypted, may overwrite the destination selected in the native dialog, and are not removed by Clear or application exit.

Destination classification uses the effective absolute HTTP target or CONNECT authority, never the replaceable `Host` header. Loopback defaults to Development; explicit exact and leading-wildcard rules classify other hosts, ambiguous Development/Production overlaps are rejected, and everything unlisted remains Unknown. Observation is allowed for all classes. The shared policy layer fails closed for active operations on both Production and Unknown, although replay, modification, routing and chaos features are not exposed yet. Future redirects and rewritten routes must be reclassified before those operations are enabled.

Response breakpoints are an explicit per-run option. They call the shared `Modify` policy and pause only Development responses. A waiting response may continue unchanged, receive a replacement final status from 200 through 599, or receive that status with a replacement UTF-8 body of at most 64 KiB and a validated `Content-Type`. Entity validators, ranges, encodings and lengths from the upstream body are removed or regenerated before a replacement is returned. It automatically continues unchanged after 15 seconds, and Stop, Clear or capture eviction releases it by dropping the pending decision. Production and Unknown responses never enter the breakpoint map.

Local CA generation requires an explicit checkbox consent. The private key and certificate are stored together as a versioned credential in the operating-system credential store; serialized secret buffers and in-memory key fields are zeroized on drop where the dependency APIs permit. The private key is never returned by an IPC command. The UI exposes metadata and can export only the public PEM certificate through a native save dialog. The engine may issue a certificate for one validated DNS name or IP address only after the destination policy classifies it as Development. Leaf certificates last at most 24 hours, never outlive the CA, and use ephemeral private keys that are zeroized on drop and never cross IPC. Production and Unknown destinations fail closed. Sippin Soda does not install the CA into any trust store and cannot infer whether a user installs an exported copy manually. Generating the CA alone does not enable CONNECT interception: a matching client trust proof, proxy authentication and a separate per-run opt-in are also required. Removing the local CA deletes Sippin Soda's credential after an explicit confirmation but cannot remove manually exported or installed copies. Credential-store availability and unlock behavior depend on the operating system and desktop session.

The TLS bridge has no insecure certificate-verification mode. The desktop route uses the operating system's platform verifier and validates the upstream certificate plus requested server name before completing downstream TLS; tests may inject an explicit root store. The inspected route offers ALPN `h2` and `http/1.1` upstream, then offers only the verified upstream selection downstream; missing or different negotiation is rejected before application data is parsed. Decrypted bytes flow only after both handshakes and that protocol check succeed. The listener creates one bounded capture per HTTP/1.1 exchange or HTTP/2 stream, fixes every upstream authority to the authorized CONNECT target, removes hop-by-hop and proxy credentials, and reuses the plain-HTTP metadata, disk-budget and JSON-redaction pipeline. HTTP/2 accepts at most 16 concurrent streams, 32 KiB received header lists and a 256 KiB per-stream send buffer. Verification failure, protocol mismatch, per-request timeout, handshake timeout, inner HTTP failure and tunnel lifetime expiry are fail-closed outcomes. The listener route is opt-in and Development-only.

TLS inspection readiness is a separate engine gate, not a user assertion. It requires explicit opt-in, ready and unexpired CA metadata, and a successful TLS handshake proving that the client accepted a leaf from the same CA. The proof is scoped to the CA fingerprint, verified hostname, client profile and leaf expiry. CA rotation, CA expiry or proof expiry requires another handshake. Even a Ready gate authorizes only Development destinations through the shared policy layer. The desktop exposes a separate per-run checkbox before enabling the CONNECT TLS bridge.

Settings exposes a bounded client trust check, not trust-store automation. After an explicit checkbox action it binds a single-use TLS endpoint to a random IPv4 loopback port for 60 seconds and shows its `https://localhost` URL. The user opens that URL in the exact browser or runtime represented by the selected local client profile. A fixed, non-cacheable confirmation response is sent only after that client accepts a `localhost` leaf from the current CA; request bytes are not read, stored or logged. The proof is bound to the selected profile ID, and readiness requested for another profile fails closed. Failure, expiry, cancellation, CA generation/removal and application exit close the listener and clear readiness. Profiles are operator-selected labels stored in local browser storage; they do not detect or authenticate operating-system processes. Success does not enable HTTPS inspection or change proxy settings.

Proxy runs can optionally require an ephemeral 256-bit token for one selected client profile using HTTP Basic proxy authentication. The desktop generates the token with the platform cryptographic random source and keeps it only in webview memory for that run; the engine receives it over local IPC, stores only its SHA-256 digest and compares presented tokens in constant time. Missing, malformed or incorrect credentials receive `407 Proxy Authentication Required` before capture creation, DNS lookup or upstream connection. `Proxy-Authorization` remains redacted and is stripped before HTTP forwarding or CONNECT upgrade. Accepted captures retain only the non-secret profile ID. Stopping the proxy discards the authentication configuration. The UI necessarily displays the token so the user can configure the client; users should treat it as a short-lived local secret and avoid placing it in shared shell history.

TLS inspection preflight derives the client profile from live engine state rather than accepting a claimed profile from the UI. It is ready only when the proxy is running with authentication, the current CA is valid and the trust proof belongs to that same profile and has not expired. Stopped, unauthenticated, missing/expired CA, missing proof and mismatched-profile states all fail closed. The route reevaluates readiness and destination class for every CONNECT. If readiness is lost, subsequent connections remain opaque; changing or removing the CA first stops the proxy and its active bridges.

The optional JSON layout is another unredacted temporary file, charged to the same budget and removed with its capture. Search and layout run locally with two concurrent analysis jobs at most. Queries are literal UTF-8 with a 4096-byte cap; each search scan reads at most 4 MiB. JSON layout enforces UTF-8, syntax and 128-level nesting checks without loading a complete document tree. Neither feature changes the forwarded body or substitutes for redaction.

Do not include credentials, private keys or unredacted traffic in public issues. Report suspected vulnerabilities through GitHub's private vulnerability reporting when enabled; otherwise contact the maintainer privately before disclosing sensitive details. A dedicated security contact and release support policy will be established before distribution.
